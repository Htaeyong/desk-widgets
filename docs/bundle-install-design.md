# 묶음 설치 설계 (#96)

> 상태: **사용자 결정 완료(2026-10-26, §7 추천안 1~8 그대로) → A안 구현함**. 합의는 정책과 합의사항의 "묶음 설치" 행, 동작은 [앱 안에서 업데이트](updates.md)의 "처음 설치할 때 위젯 고르기", 사용법은 [사용자 가이드](user-guide.md#설치)에 있습니다. 아래는 설계 당시의 비교와 상세 설계입니다.

## 1. 목표와 현재 상태

처음 쓰는 사람이 **엔진 + 고른 위젯을 한 번에** 설치할 수 있게 한다.

지금은 엔진(`DeskWidgets-Setup-<버전>.exe`, 약 112MB)을 설치한 다음, 위젯마다 설치 파일(`DeskWidgets-<제품명>-Setup-<버전>.exe`)을 따로 받아 실행해야 한다. 위젯 설치 파일을 엔진보다 먼저 실행하면 "Desk Widgets가 설치되어 있지 않습니다"라고 멈춘다.

이 설계에서 알아 둘 현재 사실:

| 사실 | 내용 |
|---|---|
| 위젯 설치 파일은 아주 작다 | 7개 모두 120~220KB(합계 약 1.1MB). 엔진만 112MB. 위젯은 엔진이 설치된 폴더 옆(`...\chilgong88\widgets\<id>`)에 파일을 복사하고 제어판 항목을 등록할 뿐이다 |
| 위젯 설치는 관리자 권한 필요 | `RequestExecutionLevel admin`, 모든 사용자(`Program Files`). 설치 파일 하나마다 UAC 창이 한 번 뜬다 |
| 설치 파일 정보는 이미 사이트에 있다 | `products.json`(widgets.chilgong88.com)의 제품마다 `download`(주소·크기·SHA-256). 인앱 업데이트([#104](updates.md))가 읽고, 해시를 확인한 뒤 `shell.openPath`로 실행(UAC) |
| 설치 안 한 위젯을 받는 길도 이미 있다 | `UpdateManager.install(id)`는 "동결 위젯의 후속 위젯(아직 설치 안 됨)"을 설치 항목으로 받아 같은 경로로 설치한다(#111) |
| 설치가 끝나면 엔진이 안다 | 위젯 설치 파일이 `--widget-installed=<id>`로 엔진에 알리고, 엔진의 위젯 폴더 감시(WidgetWatcher)가 위젯을 켠 뒤 업데이트 목록을 다시 계산한다 |
| 공개 전 위젯은 목록에 없다 | `scripts/site-build.js`가 `isUnreleasedWidget`(버전 0.0.x)을 `products.json`에서 뺀다. 할 일 노트(0.0.x)는 사이트에도, 인앱 업데이트에도 나오지 않는다 |

## 2. 안 비교

### A. 엔진 첫 실행에 위젯 고르기 화면 (권장)

엔진을 설치하고 처음 실행하면, 위젯이 하나도 없을 때 **"어떤 위젯을 쓰시겠어요?"** 화면(위젯 관리 창 안)이 뜬다. `products.json`의 위젯 카드(이름·설명·스크린샷)에서 고르고 **설치**를 누르면, 고른 위젯을 인앱 업데이트와 같은 경로(`engine/main/updates.js`: 허용 주소 확인 → 다운로드 → 크기·SHA-256 확인 → `shell.openPath`로 실행·UAC)로 **차례로** 설치한다. 새 설치 파일은 없다. 같은 화면을 위젯 관리 창의 **위젯 추가** 칸에서 언제든 다시 연다.

```
엔진 설치 파일 실행 → (UAC 1회) → 엔진 시작
  → 위젯이 없음 + 아직 안 물어봄 → "위젯 고르기"
     → products.json 읽기(widgets.chilgong88.com)
     → 고른 위젯마다: 내려받기 → 해시 확인 → 설치 파일 실행(UAC) → 폴더 감시가 위젯을 켬 → 다음 위젯
```

### B. 묶음 설치 파일 (엔진 + 위젯 포함)

NSIS 설치 파일 하나에 엔진과 위젯 패키지를 넣고, 구성 요소 선택 페이지에서 고르게 한다. 두 가지로 만들 수 있다.

- **B1. 엔진 설치 파일에 위젯을 함께 넣기**: `build/installer.nsh`에 구성 요소 페이지를 넣고 위젯 패키지를 `File`로 포함. 위젯 설치 로직(폴더 배치, 제어판 등록, 제거 프로그램, `--widget-installed`)을 엔진 NSIS 쪽에 복제해야 한다.
- **B2. 별도 "묶음 설치 파일"**: 엔진 설치 파일 + 위젯 설치 파일들을 한 파일로 묶는 부트스트래퍼. 설치 파일 하나가 더 생기고 릴리스·서명 대상도 하나 늘어난다.

## 3. 비교표

| 항목 | A. 첫 실행 고르기 | B. 묶음 NSIS |
|---|---|---|
| 새로 만드는 것 | 고르기 화면 + 순차 설치 큐 + 첫 실행 판단. 다운로드·해시·실행은 `updates.js` 재사용 | NSIS 구성 요소 페이지, 위젯 패키지 포함, 위젯 설치·제거 로직 복제(B1) 또는 새 부트스트래퍼와 릴리스 체계(B2) |
| 작업량(추정) | **작음~중간**: 엔진 코드 + 문서, 약 2~3일 | **중간~큼**: 빌드·릴리스·CI·서명 변경까지, 약 4~6일 |
| 제품별 독립 버전(정책) | **그대로 유지**. 항상 `products.json`의 현재 배포 버전을 받는다 | **충돌**. 묶음 안 위젯은 만든 시점 버전. 위젯만 바뀌어도 묶음을 다시 만들어야 하고, 안 만들면 낡은 위젯이 나간다 |
| 설치 파일 크기 | 엔진 112MB 그대로, 위젯은 고른 것만 약 0.1~0.2MB씩 | 위젯이 작아서 +1MB 정도라 **크기는 문제가 아님** |
| 오프라인 설치 | 엔진은 가능, **위젯은 인터넷 필요** | 묶음에 든 위젯은 오프라인 가능 |
| 코드 서명([#101](code-signing.md)) | 서명 파이프라인 변경 없음. 위젯 설치 파일이 각각 서명되면 `REQUIRE_SIGNATURE`로 게시자까지 확인(자리가 이미 있음). 서명 후 `releases.json` 해시를 서명본에서 기록해야 하는 과제는 #104에서 이미 알려져 있음 | 서명 대상이 늘거나(B2) 엔진 NSIS 안에 들어가는 위젯 제거 프로그램까지 서명 훅을 확장해야 함(B1). SignPath 요청·승인 횟수 증가 |
| 릴리스 절차 | 변화 없음(위젯은 지금처럼 따로) | 위젯 변경마다 묶음 재빌드·재서명·재배포 판단 필요. `release:all`, CI 워크플로, 사이트 `products.json` 모두 손봄 |
| UAC 창 횟수 | 엔진 1회 + 위젯마다 1회(위젯 3개면 총 4번). **불편 요소** | 1회 |
| 사이트·GitHub가 안 열릴 때 | 고르기 화면에서 안내하고 엔진은 정상 사용. 나중에 다시 시도 | 영향 없음(이미 파일에 있음) |
| 공개 전 위젯 노출 | `products.json`에 없고 엔진에서도 한 번 더 걸러 안 보임(§5.2) | 빌드에서 빼는 목록을 따로 관리해야 하고, 실수하면 설치 파일에 들어가 공개됨(공개 전 위젯은 GitHub 비공개 원칙 위반 위험) |
| 위험 | UAC를 거절/무시하면 큐가 멈춤(시간 제한·건너뛰기로 해결), 네트워크 의존 | 낡은 위젯 배포, 릴리스 복잡도, 위젯 설치 로직 이중화, 실수로 미공개 위젯 포함 |

## 4. 권장: A, UAC 횟수는 단계로 줄이기

**A를 권장한다.** 이유:

1. 위젯이 매우 작아서 B의 장점(한 파일, 오프라인)으로 얻는 것이 적다. 반면 B의 단점(제품별 버전 충돌, 릴리스·서명 증가, 미공개 위젯이 새어 나갈 위험)은 크다.
2. 이미 있는 부품(`products.json`의 `download`, 해시 확인, 허용 주소, `install(id)`, 폴더 감시)을 재사용한다. 새 설치 파일이 없으므로 서명 대상도 늘지 않는다.
3. 같은 화면이 **위젯 관리 창의 "위젯 추가"** 로 이어져, 나중에 위젯을 더 받을 때도 쓴다.

A의 약점은 **위젯마다 UAC가 뜬다**는 점이다.

- **1단계(이번 구현)**: 위젯을 한 번에 한 개씩 설치. 각 위젯 앞에 "두레이 대시보드 설치 (1/3) — 곧 나오는 관리자 확인 창에서 **예**를 누르세요"를 보여 준다.
- **2단계(후속, 필요하면)**: UAC 한 번으로 여러 위젯 설치. 위젯 설치 파일은 `/S`(조용히)를 받지만 `shell.openPath`는 인자를 줄 수 없으므로, 서명된 작은 도우미 실행 파일이 한 번만 올라가 해시 확인을 마친 설치 파일들을 차례로 실행하는 방식이 필요하다. 권한 상승 도우미라는 별도 보안 부담이 있어 1단계 사용성을 본 뒤 정한다.

## 5. 상세 설계 (A)

### 5.1 언제 보이나

- **위젯이 하나도 설치되어 있지 않고** 설정 `onboardingDone`이 없을 때만 자동으로 연다. 이미 위젯이 있는 기존 사용자가 엔진만 업데이트해도 뜨지 않는다.
- 닫기 / **나중에**를 누르면 `onboardingDone = true`로 기록하고 다시 자동으로 열지 않는다. 위젯 관리 창 **위젯 추가**에서 언제든 다시 연다. 위젯을 모두 지운 사용자에게도 자동으로 다시 띄우지 않는다.
- 엔진 설치 마지막의 "Desk Widgets 실행"(`runAfterFinish`)이 첫 실행이다.

### 5.2 목록을 만드는 규칙

목록은 `products.json`(`parseProducts`가 검사한 `productEntry`)에서 만든다. 아래에 걸리면 **목록에 넣지 않거나 선택할 수 없게** 한다.

| 조건 | 처리 |
|---|---|
| `download` 없음 / 주소·해시 형식 오류 | 숨김(기존 `parseProducts` 규칙) |
| **공개 전 위젯: 버전이 `0.0.x`이거나 `-test` 등 사전 릴리스** | **숨김**. 사이트가 이미 빼 주지만 엔진이 `isPublicVersion`으로 한 번 더 걸러, 사이트가 잘못 나가도 노출되지 않게 한다. 개발 실행의 로컬 시험 모드(`DESK_WIDGETS_UPDATE_URL`)에서만 예외 |
| 동결 위젯(`frozen`, 예: 할 일 노트 정식 배포 후의 할 일 목록) | 기본 숨김, 후속 위젯을 안내 |
| 이 엔진보다 높은 `engineMin`/`engineApi` 필요 | 선택 불가 + "엔진 업데이트가 필요합니다" |
| 이미 설치됨 | "설치됨"으로 표시(선택 불가) |

### 5.3 설치 순서와 상태

- 고른 위젯을 **하나씩** 실행한다(여러 설치 파일/UAC 창을 동시에 띄우지 않음). 상태: 대기 → 내려받는 중 → 확인 중 → 관리자 확인 대기 → 설치됨 / 실패 / 건너뜀.
- 완료 판단은 기존 신호(위젯이 폴더에 나타나 WidgetWatcher가 감지, `--widget-installed`)를 쓴다. 제한 시간(예: 5분) 안에 안 나타나면 "관리자 확인 창을 취소하셨나요?"와 **다시 시도 / 건너뛰기**를 보여 준다(`shell.openPath`는 UAC 취소를 알려 주지 않음).
- 실패(네트워크 끊김·해시 불일치·크기 초과·UAC 취소)한 위젯은 건너뛰고 나머지를 계속한다. 마지막에 "N개 설치됨, M개 실패(다시 시도)" 요약. 해시 불일치 파일은 기존대로 삭제.

### 5.4 연결이 안 될 때

| 상황 | 동작 |
|---|---|
| widgets.chilgong88.com이 응답하지 않음 | 목록 대신 "인터넷에 연결되지 않았거나 사이트에 접속할 수 없습니다" + **다시 시도** + **다운로드 페이지 열기**. 엔진은 위젯 없이 정상 동작 |
| 사이트는 되는데 GitHub 다운로드가 실패 | 위젯별 실패 표시 + **다시 시도**. 허용 주소(github.com 이 저장소 releases, objects/release-assets.githubusercontent.com) 밖으로는 가지 않는다 |
| 완전 오프라인 | A의 한계. 보완안: 고르기 화면에 **내려받아 둔 위젯 설치 파일 열기**(파일 선택 → 서명 확인 후 실행)를 둘 수 있음(결정 항목) |
| 업데이트 확인을 꺼 둔 사용자 | 고르기 화면은 사용자가 연 동작이므로 접속 허용. 개인정보 안내에 "위젯 고르기 화면을 열 때 products.json과 설치 파일을 받습니다"를 추가 |

### 5.5 보안

- 목록 JSON, 다운로드 주소, 크기·해시 검사는 `updates.js`의 현재 규칙을 그대로 쓴다. 렌더러는 위젯 id만 보내고 주소·경로·인자는 보내지 않는다(IPC `engine:install-update`와 같은 모양).
- 코드 서명이 켜지면 `REQUIRE_SIGNATURE`를 켜서 게시자까지 확인(자리가 이미 있음). 서명이 없는 동안은 SmartScreen이 설치 파일마다 뜰 수 있다(엔진 설치와 같음).

### 5.6 파일·문서 영향

- 엔진: `engine/main/updates.js`(설치 가능 위젯 목록 계산, 순차 큐), `engine/main/main.js`(첫 실행 판단·IPC), 렌더러(고르기 화면, 위젯 관리 창 "위젯 추가" 칸), 설정 `onboardingDone`.
- 테스트: 목록 필터(공개 전·동결·엔진 요구·설치됨), 큐 순서·실패 후 계속, 첫 실행 판단, 허용 주소 밖 거부. `scripts/update-e2e.js` 확장.
- 문서: [사용자 가이드](user-guide.md) 설치 절, [앱 안에서 업데이트](updates.md), [개인정보 안내](privacy.md), 다운로드 페이지 설치 안내, 변경 이력, 합의는 정책과 합의사항.
- 제품 버전: 바뀌는 것은 **엔진만**(엔진 API 변경 없음). 다음 버전은 구현 뒤 사용자에게 묻는다.

## 6. B를 고르게 되는 경우

"위젯까지 설치 파일 한 개로 오프라인 배포"를 꼭 원하면 B2(별도 부트스트래퍼)가 B1보다 낫다(엔진 NSIS를 건드리지 않음). 조건: ① 묶음 파일에 든 위젯 버전 목록 표기, ② 공개 전 위젯을 빌드에서 자동 제외하는 검사와 테스트, ③ 위젯 변경 때 묶음 재배포 여부를 정책에 기록, ④ SignPath 요청에 묶음 파일 추가. 지금은 이 비용을 정당화할 이점이 크지 않다.
