# 개인 클라우드 동기화 설계 (#108)

> **상태: 설계 검토(구현 전).** 이 문서는 가능성 검토와 설계안입니다. 사용자가 9장의 결정 사항을 정한 뒤 구현 이슈를 따로 만듭니다. 코드·엔진 API는 아직 바뀌지 않았습니다. 클라우드 서비스 정보는 2026-10-24에 공식 문서로 확인했고, 확인하지 못한 것은 **(미확인)** 으로 표시했습니다.

## 1. 요약

- **권장: 1단계는 "동기화 폴더" 방식.** 사용자가 이미 쓰는 OneDrive·Google Drive for desktop·Dropbox 등의 PC 프로그램이 동기화하는 폴더를 엔진에 지정하면, 엔진은 그 폴더에 파일만 읽고 씁니다. 클라우드 API·OAuth 앱 등록·심사·비밀 키가 필요 없고, 앱은 여전히 **어느 서버에도 직접 접속하지 않습니다**(개인정보 안내의 약속 유지).
- **충돌을 클라우드 프로그램에 맡기지 않습니다.** 폴더 안의 파일은 모두 "한 PC만 쓰는 파일" 또는 "내용으로 이름을 정해 바뀌지 않는 파일"이라서 OneDrive·Dropbox의 충돌 사본이 생기지 않습니다. 같은 항목을 두 PC에서 고친 경우는 엔진이 항목 단위 3방향 비교로 찾아 **비교 화면에서 사용자에게 묻습니다**(요구 2).
- **2단계(선택)는 클라우드 API 직접 연결 1~2곳.** 공개 데스크톱 앱이 PKCE로 앱 전용 폴더만 쓸 수 있는 **OneDrive(앱 폴더)** 와 **Google Drive(`drive.appdata`, 민감하지 않은 범위라 앱 심사 불필요)** 가 가장 현실적이고, **Dropbox(App Folder)** 는 연결 사용자 50명이 넘으면 승인 심사가 필요합니다. **NAVER WORKS 드라이브·두레이 드라이브 API는 개인용 공개 앱으로는 비현실적**입니다(2장). 둘 다 PC 프로그램의 동기화 폴더로는 쓸 수 있습니다.
- **비밀번호·토큰은 동기화하지 않습니다**(기본). 원하면 3단계에서 사용자 암호(패스프레이즈)로 종단 암호화한 묶음만 동기화하는 선택 기능을 둡니다.
- **동기화 설정은 엔진에** 있습니다(요구 3). 위젯은 "무엇을 어떤 단위로 동기화할 수 있는지"만 선언하고(엔진 API 1.7), 연결·주기·충돌 화면은 엔진이 맡습니다.

### 2.2 동기화 폴더(API 없이)

사용자가 이미 설치한 PC 프로그램이 동기화하는 폴더를 고르면, 엔진은 로컬 파일만 다룹니다. 등록·심사·토큰·요청 한도가 없고, 앱은 어떤 서버에도 접속하지 않습니다.

| 서비스 | Windows PC 프로그램 | 폴더 모양 | 주의 |
|---|---|---|---|
| OneDrive | Windows에 기본 포함 | 일반 폴더(`%OneDrive%`), 파일 주문형(자리 표시자) | 충돌 시 `파일-컴퓨터이름.확장자` 사본(비공식 자료, **(미확인)**). 무료 5GB |
| Google Drive | Drive for desktop | **스트리밍**(가상 드라이브, 온라인 전용 파일) 또는 **미러링**(일반 로컬 폴더) | 스트리밍 기본 드라이브 문자(G:)·충돌 사본 이름 **(미확인)**. 미러링 권장 |
| Dropbox | Dropbox 데스크톱 | 일반 폴더, 온라인 전용 파일 가능 | 충돌 시 "(이름의 conflicted copy 날짜)". Basic은 기기 3대 |
| NAVER WORKS 드라이브 | Drive Explorer | 가상 드라이브 `W:` 또는 1:1 폴더 동기화(폴더 20개, PC 3대) | Drive 또는 Standard 요금제 필요. 충돌 처리 **(미확인)** |
| 두레이 드라이브 | 드라이브 동기화 앱(**베타**, Windows 10 1709+, 일반 환경만) | 동기화 폴더, "공간 절약" 모드 | 충돌 처리 **(미확인)** |

이 방식은 클라우드마다 다른 충돌 사본·자리 표시자 동작을 견뎌야 합니다. 그래서 4.4의 구조(한 파일은 한 PC만 쓰고, 공용 파일은 내용 해시 이름)로 충돌 사본이 생길 일 자체를 없애고, 덜 받아진 파일은 건너뛰고 다음에 다시 읽습니다(4.6).

### 2.3 판정

- **1단계 동기화 폴더**: OneDrive·Google Drive(미러링 권장)·Dropbox·NAVER WORKS·두레이(동기화 앱이 있는 경우) 모두 같은 코드로 됩니다. 비용·심사·비밀 키 문제가 없어 가장 현실적입니다.
- **2단계 API 후보**: OneDrive(앱 폴더, 비밀 없음, 등록 무료) 또는 Google Drive(`drive.appdata`, 민감하지 않은 범위라 심사 없이 프로덕션 게시 가능). Dropbox도 되지만 50명이 넘으면 승인 심사가 필요하고 무료는 기기 3대.
- **NAVER WORKS·두레이 API**: 공개 개인 앱으로는 하지 않음. 쓰려면 그 PC 프로그램의 동기화 폴더로.

## 3. 무엇을 동기화하나

원칙:

1. **사용자가 만든 내용**(할 일, 내 캘린더 일정, 노트, 분류, 알람)은 동기화합니다.
2. **PC마다 달라야 하는 것**(창 위치·크기, 열린 창, 모니터에 따른 배치, 자동 실행, Win+D 방식, 노트 폴더 경로)은 동기화하지 않습니다. 모니터 구성이 다른 PC에 창 위치를 옮기면 화면 밖으로 나갑니다.
3. **비밀 값**(DPAPI로 암호화한 토큰·비밀번호)은 동기화하지 않습니다. DPAPI 값은 그 PC·그 Windows 사용자만 풀 수 있어 옮겨도 쓸 수 없고, 풀어서 올리면 평문이 됩니다. 3단계 선택 기능(종단 암호화)만 예외입니다(6장).
4. **다시 만들 수 있는 것**(메일 헤더 캐시, CalDAV 캐시, 업데이트 확인 기록)은 동기화하지 않습니다.
5. 설정 값은 위젯이 **공유(shared)** 로 표시한 것만 동기화하고, 표시하지 않은 값은 **PC별**이 기본입니다(새 설정이 실수로 퍼지지 않게).

### 3.2 위젯별

| 위젯 | 동기화(항목 단위) | 공유 설정 | PC별·제외 |
|---|---|---|---|
| **할 일** | `settings.json`의 `lists`(id), `tasks`(id). 출처 링크(`source`) 포함 | 테마, 다시 알림 분, 연동 스위치 3개 | 항상 위, 선택한 목록, 창 위치. `remindedFor`·`snoozedUntil`은 공유(다른 PC가 같은 알림을 또 띄우지 않게. 두 PC가 동시에 켜져 있으면 동기화 간격만큼 겹칠 수 있음) |
| **캘린더** | `local-events.json`의 `events`(uid `local:…`) | 주 시작 요일, 다가오는 일정 기간, 갱신 주기, 내 캘린더 켜기, 완료 할 일 표시, 테마·불투명도, **계정 목록**(CalDAV 주소·아이디·이름·색, 비밀번호 제외) | `secrets.json`(제외), `cache\`(제외), 창·테마 창 위치, `lastCalendar`. **ICS 구독 주소**는 주소 안에 비밀 토큰이 든 경우가 많아(예: Google 비공개 주소) 기본 제외, 3단계 암호화 묶음으로만 |
| **메일** | `categories.json`(분류 id, 지정은 계정 id + Message-ID), `contacts.json`(주소를 소문자로 한 키) | 계정 목록(서버·포트·아이디·표시 이름·서명 등, 비밀번호 제외), 갱신 주기, 읽음 처리, 알림, 테마 | `secrets.json`(제외), `cache\`(제외), 창 위치. 주소록의 "사용 횟수·마지막 사용"은 두 PC 값 중 큰 값으로 합침(충돌로 묻지 않음) |

| **시계** | 알람(id) | 초 표시, 12시간제, 도구 탭, 타이머 프리셋, 테마 | 항상 위, 창 위치, 실행 중인 스톱워치·타이머 상태, 마지막 탭, 알람 처리 시각 |

**업무 데이터 주의:** 두레이 분류의 업무 지정에는 업무 제목 사본이, 메일 분류·주소록에는 메일 주소가 들어 있습니다. 이것을 개인 클라우드에 올리면 회사 보안 정책에 어긋날 수 있습니다. 그래서 **두레이·메일 데이터는 위젯별 동기화 스위치를 기본 꺼짐**으로 두고, 켤 때 이 점을 알립니다(결정 사항 D5).

## 4. 데이터 모델

### 4.1 항목 레코드

위젯이 선언한 컬렉션(예: 할 일의 `tasks`)의 항목 하나와 공유 설정 키 하나가 각각 **레코드**입니다. 엔진은 레코드마다 메타데이터를 붙여 관리합니다(위젯 파일 안에는 넣지 않고 엔진의 `sync\` 폴더에 따로 둠).

```jsonc
{
  "key": "todo/tasks/t-8f2c",       // 위젯 id / 컬렉션 / 항목 id (설정이면 "todo/@settings/snoozeMinutes")
  "rev": { "n": 42, "device": "d-3fa9c1" }, // 논리 시계(램포트 카운터) + 마지막으로 바꾼 PC
  "updatedAt": 1761300000000,        // 바꾼 PC의 시계(표시용, 순서 판단에 쓰지 않음)
  "hash": "sha256:…",                // 항목 값을 정규화(JSON 키 정렬)한 해시
  "deleted": false,                  // true면 삭제 표시(tombstone), value 없음
  "value": { … }                     // 항목 값 (위젯 sanitize를 거친 모양)
}
```

- **id**: 위젯이 이미 쓰는 고유 id를 그대로 씁니다(할 일·목록 id, 캘린더 `local:<24hex>`, 노트 머리말 id, 분류 id, 메일 주소). 시계 알람도 이미 id가 있습니다. id가 없는 데이터가 새로 생기면 위젯이 id를 붙이도록 바꿉니다.
- **해시**: "바뀌었나"는 해시로 판단합니다. 값이 같으면 시각·PC가 달라도 충돌이 아닙니다.
- **삭제 표시(tombstone)**: 지운 항목은 `deleted: true`로 남깁니다. 그래야 꺼져 있던 PC가 "이 PC에 없으니 받아온다"(요구 1)·"클라우드에 없으니 올린다"로 되살리지 않습니다. 삭제 표시는 **180일** 보관 뒤 지우고(결정 사항 D6), 그보다 오래 동기화하지 않은 PC는 다시 연결할 때 "처음 연결"처럼 비교 화면을 거칩니다(되살아날 항목이 무엇인지 보여 주고 묻기).

### 4.2 PC 시계 차이

- 순서는 **논리 시계**로 정합니다. 항목을 바꿀 때 `rev.n = (이 PC가 본 가장 큰 n) + 1`. PC 시계가 틀려도 순서가 뒤집히지 않습니다.
- `updatedAt`은 비교 화면에 "언제 바꿨는지" 보여 주는 용도입니다. 다른 PC의 `updatedAt`이 이 PC 시각보다 5분 넘게 미래면 비교 화면에 "그 PC의 시계가 맞지 않을 수 있음"을 표시합니다.
- 램포트 카운터가 같고 내용이 다르면(동시에 바꿈) 그것이 바로 충돌입니다(4.3).

### 4.3 충돌 감지: 마지막 동기화 기준과 3방향 비교

엔진은 이 PC에 **기준 사본**(base: 마지막으로 동기화를 마쳤을 때 레코드별 해시와 rev)을 둡니다. 레코드마다:

| 이 PC (기준 대비) | 클라우드 (기준 대비) | 처리 |
|---|---|---|
| 그대로 | 그대로 | 아무것도 안 함 |
| 바뀜 | 그대로 | 이 PC 값을 올림 |
| 그대로 | 바뀜 | 클라우드 값을 받음(이 PC에서 잃는 변경이 없으므로 묻지 않음, 결정 사항 D3) |
| 바뀜 | 바뀜, 해시 같음 | 같은 결과라 기준만 갱신 |
| 바뀜 | 바뀜, 해시 다름 | **충돌 → 비교 화면** |
| 없음(기준에도 없음) | 있음 | 받아옴 (요구 1) |
| 있음(기준에 없음) | 없음 | 올림 |
| 지움 | 바뀜 | **충돌**("다른 PC에서 고친 항목을 이 PC에서 지웠습니다") |
| 바뀜 | 지움 | **충돌** |

요구 2의 "최신 항목으로 받아오되 덮어써야 하면 묻기"는, **이 PC에만 있는(아직 올리지 않은) 변경이 사라지는 경우**를 "덮어쓰기"로 봅니다. 이 PC에서 고치지 않은 항목이 다른 PC에서 더 새로 바뀐 것은 사용자 자신의 최신 작업이라 묻지 않고 받습니다. 모든 받아오기를 확인받고 싶으면 설정 "받아오기 전 항상 확인"을 켭니다(D3).

여러 PC(3대 이상): 클라우드 쪽 값은 다른 PC들의 레코드 중 `rev`가 가장 앞선 것(n이 크고, 같으면 device id 순)입니다. 다른 PC끼리 이미 충돌이 있으면(n이 같고 해시가 다름) 그 후보들을 모두 비교 화면에 보여 줍니다.

**병합 규칙이 정해진 필드**는 충돌로 묻지 않습니다: 메일 주소록 사용 횟수(큰 값), 할 일 `completedAt`(완료가 미완료보다 우선은 하지 않음: 사용자가 다시 미완료로 돌렸을 수 있으므로 일반 충돌로 둠). 필드 단위 자동 병합은 1단계에서 하지 않고 항목 단위로만 비교합니다(단순하고 예측 가능하게).

### 4.4 클라우드 폴더 구조

```
<동기화 폴더>\Desk Widgets Sync\
  format.json                         # { "format": 1 } 형식 버전. 더 높은 형식이면 이 PC는 읽기만 하고 업데이트 안내
  devices\
    d-3fa9c1.json                     # { id, name: "회사 PC", lastSync, engineVersion } - 그 PC만 씀
  state\
    d-3fa9c1\
      todo.json                       # 그 PC가 아는 todo 레코드 전체(4.1 모양) - 그 PC만 씀
      calendar.json
      memo.json                       # 노트 레코드: 내용 대신 blob 해시
      engine.json
  blobs\
    ab\ab12…ef.md                     # 내용 해시로 이름을 정한 파일(노트 본문, 첨부). 한번 쓰면 바뀌지 않음
    9c\9c40…11.png
```

- **한 파일에는 한 PC만 씁니다**(`devices\<id>`, `state\<id>\`). 클라우드 프로그램 입장에서 동시 수정이 없으므로 충돌 사본이 생기지 않습니다. 각 PC는 다른 PC들의 `state` 파일을 모두 읽어 4.3대로 합친 뒤 자기 `state`를 다시 씁니다.
- **blob은 내용 해시가 이름**이라 같은 이름이면 같은 내용입니다. 두 PC가 같은 파일을 올려도 충돌이 아닙니다. 어떤 PC의 `state`도 가리키지 않는 blob은 30일 뒤 정리합니다.
- 상태 파일 크기: 할 일 1,000개 ≈ 300KB, 일정 10,000개 ≈ 3MB 정도로 작습니다. 레코드가 많아지면 컬렉션을 해시 앞자리로 나누는 것은 나중 과제입니다.
- 사람이 클라우드 폴더를 열어 보면 노트는 blob 이름이라 읽기 어렵습니다. 노트를 클라우드에서 바로 읽고 싶으면 지금처럼 **노트 폴더 자체를 OneDrive 안으로 지정**하는 방법(이미 지원, #75)이 있고, 이 경우 노트는 엔진 동기화에서 빼야 합니다(두 방식이 같은 파일을 다루면 안 됨, 4.5).

### 4.5 노트(파일) 동기화

- 노트 하나 = 레코드 하나: `value`는 `{ path(노트 폴더 기준 상대 경로), blob(본문 해시), assets: { 상대 경로: 해시 }, archived }`. 노트 id는 이미 있는 md 머리말 `desk-widgets-memo:` id를 씁니다(머리말 없는 .txt 등은 위젯이 기억하는 경로 id).
- 이름 바꾸기·보관함 이동은 `path`만 바뀐 것이라 내용 충돌이 아닙니다. 두 PC가 같은 노트의 **본문**을 다르게 고쳤을 때만 충돌입니다. 비교 화면은 두 본문의 줄 단위 차이를 보여 줍니다.
- 받아온 노트를 노트 폴더에 쓸 때는 지금 노트 저장과 같은 **임시 파일 → fsync → 이름 바꾸기**를 쓰고, 그 노트 창에 저장하지 않은 내용이 있으면 이미 있는 "바깥 변경" 선택(바뀐 내용 보기 / 내 내용으로 저장 / 사본으로)으로 넘깁니다.
- **노트 폴더가 이미 클라우드 동기화 폴더 안이면** 엔진 동기화에서 노트를 자동으로 빼고 "노트 폴더는 OneDrive가 이미 동기화하고 있습니다"라고 알립니다(같은 파일을 두 동기화가 다루면 충돌 사본·중복이 생김).
- 노트 첨부 크기 제한: 파일 하나 20MB, 전체는 클라우드 무료 용량을 생각해 경고만(D7).

### 4.6 원자적 쓰기와 반쯤 올라간 파일

- **쓰기 순서**: blob 먼저 → `state\<id>\*.json` → `devices\<id>.json`. 상태 파일이 가리키는 blob은 항상 먼저 있습니다.
- **파일 하나 쓰기**: 같은 폴더의 `.<이름>.tmp-<임의>`에 쓰고 fsync 후 이름 바꾸기. 읽는 쪽은 `.tmp-` 파일을 무시합니다. 클라우드 프로그램이 임시 파일을 잠깐 올렸다 지우는 것은 무해합니다.
- **읽기 검사**: 상태 파일에는 `{ format, device, written, count, sha256 }` 머리를 두고 본문 해시가 맞을 때만 씁니다. 다른 PC 파일이 아직 덜 받아졌거나(클라우드 프로그램이 내려받는 중) 깨졌으면 그 PC는 이번 회차에서 건너뛰고 "회사 PC의 데이터를 아직 받는 중"으로 표시, 마지막으로 읽은 정상 사본을 씁니다.
- **blob이 아직 없으면**(상태는 왔는데 첨부가 덜 내려옴) 그 노트만 다음 회차로 미룹니다.
- **잠긴 파일**(OneDrive가 올리는 중): 노트 저장과 같이 짧게 다시 시도.
- **이 PC 쪽 적용**: 받아온 결과는 위젯 저장 파일에 기존 `createStore`의 쓰기로 한 번에 반영하고, 성공한 뒤에만 기준 사본을 갱신합니다. 중간에 꺼지면 다음 동기화가 같은 비교를 다시 해서 같은 결과가 됩니다(멱등).
- 2단계 API 방식도 같은 구조를 쓰고, 덮어쓰기에는 서비스의 조건부 쓰기(ETag·rev)를 더합니다.

### 5.2 처음 연결 (요구 1)

1. **동기화 켜기** → 방식 고르기: 동기화 폴더(1단계) / 클라우드 계정(2단계).
2. 폴더 고르기: 엔진이 알려진 위치를 찾아 후보로 보여 줍니다(OneDrive는 환경 변수 `%OneDrive%`·`%OneDriveConsumer%`, Dropbox는 `%APPDATA%\Dropbox\info.json`의 경로, Google Drive for desktop은 설정한 드라이브 문자 또는 미러 폴더). 고른 폴더 아래에 `Desk Widgets Sync`를 만듭니다. 고른 곳이 동기화 프로그램 폴더로 보이지 않으면 "이 폴더는 다른 PC로 옮겨지지 않을 수 있습니다" 경고.
   - 설정 폴더(`%APPDATA%\chilgong88\desk-widgets`)·설치 폴더·노트 폴더 안은 거절(노트 폴더 설정과 같은 규칙).
3. 이 PC 이름(기본: 컴퓨터 이름).
4. **검사**: 폴더에 다른 PC의 데이터가 없으면 "첫 PC"로 이 PC 데이터를 올리고 끝. 있으면 미리 보기를 보여 줍니다.

```
┌ 동기화 시작: 무엇이 바뀌는지 ─────────────────────────┐
│ 클라우드에서 받아올 것 (이 PC에 없음)                    │
│   할 일 12개 · 내 캘린더 일정 30개 · 노트 5개 · 알람 2개   │
│ 클라우드에 올릴 것 (클라우드에 없음)                      │
│   할 일 3개 · 노트 1개                                    │
│ 양쪽에 있는데 다른 것 → 비교가 필요합니다                  │
│   할 일 1개 · 설정 4개(테마, 갱신 주기 …)                  │
│                                                           │
│         [취소]            [계속: 받기·올리기 후 비교하기]   │
└───────────────────────────────────────────────────────────┘
```

처음 연결에는 기준 사본이 없으므로 "양쪽에 있는데 다른 것"은 모두 충돌로 다룹니다. 서로 모르는 두 PC의 기본 목록처럼 **같은 id에 다른 값**은 비교 화면으로, 이름은 같지만 id가 다른 것(두 PC에서 각각 만든 "업무" 분류)은 둘 다 남깁니다(이름 같은 것 합치기는 결정 사항 D8).

### 5.3 비교 화면 (요구 2)

동기화할 때 충돌이 있으면 그 레코드는 **적용하지 않고 보류**하고(나머지는 진행), 알림 카드 "동기화: 확인할 항목 3개"와 위젯 관리 창 상태로 알립니다. 사용자가 **비교하기**를 누르면:

```
┌ 동기화 비교 (3개 중 1) ───────────────────────────────────────────┐
│ 할 일 › "주간 보고 정리"                                            │
│                                                                    │
│  이 PC (회사 PC)              │  클라우드 (집 PC)                    │
│  오늘 09:12 수정              │  어제 22:40 수정                     │
│ ─────────────────────────────┼─────────────────────────────────── │
│  제목  주간 보고 정리          │  제목  주간 보고 정리               │
│  목표  10/25(토) 18:00   ◀달라짐│  목표  10/27(월)          ◀달라짐  │
│  목록  업무                    │  목록  업무                         │
│  완료  —                      │  완료  —                            │
│                                                                    │
│ ( ) 이 PC 것 유지   ( ) 클라우드 것 받기   ( ) 둘 다 남기기          │
│ [ ] 남은 2개에도 같은 선택 적용 (같은 위젯만 / 모두)                  │
│                                                                    │
│      [나중에]        [◀ 이전]  [다음 ▶]        [적용]               │
└────────────────────────────────────────────────────────────────────┘
```

- 위젯이 항목을 사람이 읽는 줄로 바꿔 주는 함수(`describe`, 7장)를 제공하고, 엔진은 달라진 줄에 표시만 합니다. 노트는 줄 단위 차이(추가 초록·삭제 빨강), 설정은 "갱신 주기 45초 ↔ 60초"처럼 한 줄.
- 삭제 충돌은 "집 PC에서 지움 ↔ 이 PC에서 고침" + 선택지 "지우기 / 이 PC 것 유지".
- **둘 다 남기기**: 클라우드 것을 새 id로 복사해 추가(할 일·일정은 제목 뒤에 "(집 PC)", 노트는 `제목 (집 PC).md`). 설정 값은 둘 다 남길 수 없어 이 선택지를 숨김.
- **나중에**: 계속 보류. 보류 중인 항목은 이 PC 값이 그대로 쓰이고 클라우드에는 이 PC의 이전 값(기준)이 남습니다. 다른 항목은 계속 동기화됩니다.
- 적용 뒤 결과를 다시 읽어 확인하고, 선택은 로그(`sync\log.json`, 최근 200건)에 남깁니다. "이 PC 것 유지"로 사라진 클라우드 값도 로그에서 30일 동안 되살릴 수 있게 합니다(실수 방지, D9).

### 5.4 주기와 오프라인

- **이 PC에서 바뀔 때**: 위젯이 저장하면 10초 뒤(연속 저장은 모아서) 올리기.
- **받기**: 엔진 시작, 잠금 해제·절전 복귀, 2분마다 폴더 변경 확인(`fs.watch` + 파일 크기·시각 비교. Google Drive 스트리밍 드라이브 등은 감시 알림이 안 올 수 있어 주기 확인이 기준). 실제 비교는 다른 PC의 `devices\*.json`·`state` 머리가 바뀌었을 때만.
- 자리 비움·잠금 중에는 기존 갱신 정책(#6)처럼 멈추고 돌아오면 바로 확인.
- **오프라인·폴더 없음**: 동기화 폴더는 로컬 폴더라 인터넷이 끊겨도 쓰기는 성공합니다(클라우드 프로그램이 나중에 올림). 폴더가 사라졌거나(드라이브 분리, OneDrive 로그아웃) 쓸 수 없으면 "동기화 폴더를 찾을 수 없음"을 표시하고 로컬 사용은 그대로, 다시 생기면 이어서.
- **오류**: 위젯 관리 창 상태 줄과 트레이에만. 같은 오류로 알림 카드를 반복하지 않음(하루 한 번).
- 2단계 API 방식은 올리기 30초 모음, 받기 5분 + 시작·복귀 때(요청 수는 2장의 한도보다 훨씬 적음).

## 6. 비밀 값과 종단 암호화

| 방법 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 제외(권장 기본)** | 토큰·비밀번호는 PC마다 입력. 다른 PC에서 받아온 계정은 "이 PC에서 비밀번호 입력 필요"로 표시 | 클라우드에 비밀이 없음. 지금 보안 원칙(평문 저장 없음) 그대로 | PC마다 한 번씩 입력 |
| **B. 비밀만 암호로 묶어 동기화(선택, 3단계)** | 사용자가 정한 **동기화 암호**에서 scrypt(Node 내장)로 키를 만들고 AES-256-GCM으로 비밀 묶음(`secrets.bin`)만 암호화. 키는 각 PC에서 DPAPI로 저장해 다시 묻지 않음 | 한 번 입력으로 모든 PC. 클라우드 회사·폴더를 본 사람도 풀 수 없음 | 암호를 잊으면 비밀은 복구 불가(다시 입력하면 됨). 약한 암호는 무차별 대입에 약함 → 최소 길이·강도 표시. 암호를 바꾸면 모든 PC에서 다시 입력 |
| C. 전체 데이터 암호화 | 할 일·노트까지 모두 암호화 | 클라우드에 평문 없음 | 노트를 클라우드·다른 프로그램에서 볼 수 없음(#75의 방향과 반대), 암호 분실 시 동기화 데이터 전체 복구 불가(각 PC 사본은 남음). **권장하지 않음**, 원하면 결정 D4 |

- B의 묶음에 들어가는 것: 두레이 API 토큰, 캘린더·메일 계정 비밀번호, ICS 비공개 주소. 2단계의 클라우드 OAuth 토큰은 **절대 넣지 않음**(그 클라우드에 그 클라우드 열쇠를 두는 셈).
- 엔진이 강제: `createStore`의 `secret` 필드와 위젯이 `secret: true`로 표시한 값은 B가 꺼져 있으면 동기화 대상에서 빠집니다(위젯이 실수로 공유 표시해도).

## 7. 엔진 API (1.7 제안)

### 7.1 저장소에 동기화 선언

```js
const store = ctx.createStore({
  file: path.join(ctx.dataDir, 'settings.json'),
  defaults: M.DEFAULTS,
  sanitize: M.sanitize,
  // 1.7: 없으면 이 저장소는 동기화하지 않음(지금과 같음)
  sync: {
    name: 'todo',                                  // 위젯 안에서 저장소 이름
    collections: { tasks: { id: 'id' }, lists: { id: 'id' } }, // 배열 필드와 항목 id 키
    shared: ['themeId', 'themeOpacity', 'snoozeMinutes', 'receiveDooray', 'receiveMail', 'shareCalendar'],
    // 나머지 필드는 PC별. secret 필드는 항상 제외
    describe: (kind, value, locale) => [{ label: '제목', text: value.title }, …], // 비교 화면용
    copy: (value) => ({ ...value, id: newId(), title: `${value.title} (복사)` }), // "둘 다 남기기"
  },
});
store.onRemoteChange(() => refresh());  // 동기화가 파일을 바꾼 뒤(엔진이 캐시를 비우고 호출)
```

- 객체 모양 컬렉션(`memos: { id: {...} }`, 분류의 `assignments`)은 `{ map: true }`로 선언합니다.
- 엔진은 `save()` 앞뒤 값을 비교해 바뀐 레코드의 rev를 올립니다. 위젯 코드는 지금처럼 `save()`만 부르면 됩니다.
- 동기화가 적용할 값도 위젯의 `sanitize`를 거칩니다(다른 PC·다른 버전이 쓴 값을 그대로 믿지 않음).

### 7.2 직접 만든 저장소(분류, 주소록, 규칙)

`ctx.createStore`를 쓰지 않는 저장소(두레이·메일 `CategoryStore`, 메일 `ContactBook`, 두레이 `RuleStore`)는 둘 중 하나:

1. `ctx.createStore`로 옮기기(권장, 파일 모양 유지), 또는
2. 어댑터 등록: `ctx.sync.register({ name, load: () => data, save: (data) => …, collections, shared, describe })`.

### 7.3 파일 폴더 동기화(스티키 노트)

```js
ctx.sync.registerFolder({
  name: 'notes',
  dir: () => notesDir(),                 // 바뀔 수 있음
  include: (rel) => /\.(md|txt)$/i.test(rel) || /\.assets[\\/]/.test(rel),
  idOf: (rel, text) => frontMatterId(text) || pathId(rel), // 이름 바꾸기를 따라가는 id
  beforeWrite: (rel) => session.flush(rel),  // 열린 창 먼저 저장
  onRemoteChange: (changes) => library.reload(changes),
  maxFileBytes: 20 * 1024 * 1024,
});
```

### 7.4 버전과 호환

- 엔진 API **1.7**: `createStore`의 `sync`·`onRemoteChange`, `ctx.sync.register`·`registerFolder`·`ctx.sync.status()`. 지금 문서 기준 1.6에 **추가만** 하므로 1.0~1.6 위젯은 그대로 동작합니다.
- 동기화를 선언하지 않은 위젯(예전 버전)은 동기화 칸에 "이 위젯 버전은 동기화를 지원하지 않음 · 업데이트" 로 표시하고 그 데이터는 손대지 않습니다.
- 동기화를 쓰는 위젯이 1.6 엔진에서 돌아야 하면 `sync` 옵션을 넘겨도 무시되게(예전 `createStore`는 모르는 옵션을 무시함) `"engineApi": "1.6"`을 유지하고 `ctx.sync`가 있을 때만 등록하는 방식도 가능합니다. 이러면 위젯만 먼저 업데이트한 사용자도 문제없습니다(권장).
- 1.1.0부터 엔진과 위젯을 같은 버전으로 내므로, 동기화는 다음 공동 버전에 함께 들어갑니다. **버전 번호는 구현 전에 사용자에게 묻습니다.**
- `docs/widget-dev.md`의 4장 제목이 아직 "엔진 API 1.5"로 되어 있어(코드는 1.6), 구현 때 같이 고칩니다.

### 7.5 이전(마이그레이션)

- 동기화를 처음 켤 때 엔진이 각 위젯 저장소에서 레코드를 만들고 rev `n=1`, 이 PC id로 시작합니다. 위젯 파일 모양은 바꾸지 않습니다(메타데이터는 엔진의 `sync\` 폴더).
- 지금 데이터는 모두 항목 id가 있습니다(할 일·목록·내 캘린더·알람·분류·규칙·노트 머리말). 앞으로 id가 없는 데이터가 생기면 그 위젯의 `upgrade`에서 id를 붙입니다.
- 동기화를 끄면 `sync\` 폴더와 기준 사본만 지우고 위젯 데이터는 그대로. 클라우드 폴더의 이 PC 파일은 "클라우드에서 지우기"를 눌렀을 때만 지웁니다.
- 제거 프로그램의 "설정도 삭제"는 `sync\`도 지우지만 클라우드 폴더는 건드리지 않습니다(사용자 파일).

## 8. 개인정보와 보안

### 8.1 개인정보 안내(`docs/privacy.md`)에 더할 것 (구현 때)

- 요약: "동기화를 켜면 사용자가 고른 폴더(또는 연결한 클라우드 계정)에만 위젯 데이터를 씁니다. 개발자 서버로는 보내지 않습니다."
- "위젯이 접속하는 곳" 표에 **엔진(동기화)** 행: 1단계는 "접속하지 않음 — 고른 폴더에 파일만 씀, 업로드는 사용자의 OneDrive 등 프로그램이 함", 2단계는 연결한 클라우드의 API 주소와 OAuth 로그인 주소.
- "이 PC에 저장하는 것"에 `sync\`(기준 사본, 로그, 2단계 토큰은 DPAPI 암호화).
- 동기화되는 것 / 되지 않는 것 목록(3장 요약), 비밀 값은 기본 제외, 선택한 경우 사용자 암호로만 풀 수 있게 암호화.
- 두레이·메일 데이터를 개인 클라우드에 올릴 때의 회사 정책 주의.
- 지우기: 동기화 끄기·클라우드에서 지우기의 범위.

### 8.2 위협과 대응

| 위협 | 대응 |
|---|---|
| 클라우드 계정이 털림 / 클라우드 회사가 봄 | 비밀 값은 올리지 않음(또는 사용자 암호로 암호화). 할 일·노트 등은 평문이라는 점을 동기화 켤 때 알림. 전체 암호화는 D4 |

| 버그·잘못된 선택으로 대량 덮어쓰기 | 한 번에 레코드의 30% 이상 또는 20개 넘게 바뀌면 적용 전에 확인(정책 "큰 변경은 확인"), 선택 로그와 30일 되살리기 |
| 2단계 OAuth 토큰 유출 | 앱 전용 폴더 권한만(전체 드라이브 권한 요청 안 함), refresh token은 DPAPI(`createStore` secret 방식), 로그·테마·화면에 없음, 연결 끊기 때 토큰 폐기 요청 |
| 공개 저장소의 클라이언트 비밀 | PKCE 공개 클라이언트만 사용(OneDrive·Dropbox는 비밀 없음). Google 데스크톱 클라이언트의 비밀 문자열은 Google이 비밀로 취급하지 않는다고 밝혀 넣어도 되지만, 남이 같은 클라이언트 id로 우리 앱인 척하는 것은 막을 수 없음(앱 전용 폴더 범위라 피해는 그 폴더로 한정). 비밀이 필수인 NAVER WORKS는 하지 않음 |
| 테마가 동기화 데이터에 접근 | 테마는 지금처럼 위젯이 준 화면 데이터만 받음. 동기화 API는 메인 프로세스에만 |

## 9. 권장안과 단계

### 9.1 단계

| 단계 | 범위 | 작업 규모(추정) |
|---|---|---|
| **1단계: 동기화 폴더** | 엔진 동기화 핵심(레코드·rev·기준 사본·3방향 비교·삭제 표시·원자적 쓰기·폴더 감시), 위젯 관리 창 동기화 칸·처음 연결·비교 화면·트레이, 엔진 API 1.7, 할 일·캘린더(내 캘린더·계정 목록)·시계·엔진 설정 적용, 개인정보 안내·문서·테스트(두 PC를 흉내 내는 임시 폴더 2개로 자동 테스트) | 엔진 핵심 6~8일, 화면 3~4일, 위젯 적용 위젯당 0.5~1일, 실기기 2대 확인 1~2일 → **약 2.5~3주** |
| 1단계 이어서 | 스티키 노트 파일 동기화(blob·첨부·열린 창·노트 폴더가 이미 클라우드인 경우), 두레이·메일(분류·주소록·규칙, 저장소를 `createStore`로 옮기기) | 노트 4~5일, 두레이·메일 3~4일 |
| **2단계: 클라우드 API 1~2곳** | 엔진 공용 OAuth(루프백 + PKCE, #67과 공유 가능), 같은 폴더 구조를 API로(앱 전용 폴더), 조건부 쓰기, 토큰 보관·연결 끊기 | 공용 OAuth 3~4일 + 클라우드당 4~6일. 앱 등록·심사 대기 별도(사용자 작업) |
| **3단계: 비밀 값 암호화 동기화** | 동기화 암호, scrypt + AES-GCM 묶음, 암호 바꾸기·잊었을 때 | 3~4일 |

1단계만으로 OneDrive·Google Drive·Dropbox·(PC 프로그램이 폴더를 동기화한다면) 그 밖의 서비스까지 쓸 수 있어, 2단계는 "PC 프로그램을 설치하지 않은 사람"을 위한 것입니다. 2단계를 할지는 1단계를 써 본 뒤 정하는 것을 권합니다.

### 9.2 #67(OAuth 로그인)과 겹치는 것

- 루프백 리디렉션 + PKCE 로그인 창, 토큰 DPAPI 보관, 갱신·폐기는 **엔진 공용 모듈**(`ctx.oauth` 등)로 만들면 메일·캘린더(#67)와 동기화(2단계)가 함께 씁니다.
- 앱 등록은 서비스별로 하나를 공유할 수 있지만, Gmail 범위(민감·제한 범위라 앱 인증이 필요할 수 있음)와 Drive `drive.appdata`(민감하지 않음, 심사 불필요)를 한 Google 프로젝트에 넣으면 심사가 무거운 쪽을 따릅니다. **Google은 동기화용과 메일용 등록을 나누는 것**을 권합니다(Gmail 범위의 심사 조건은 이번에 확인하지 않음, #67에서 확인). Microsoft는 한 등록에 `Files.ReadWrite.AppFolder`와 메일 범위를 함께 둬도 됩니다.

### 9.3 사용자가 정할 것

| # | 결정 | 권장 |
|---|---|---|
| D1 | 1단계를 동기화 폴더 방식으로 시작할지 | 예 |

## 10. 확인하지 못한 것

2장의 **(미확인)** 표시 외에:

- Google Drive for desktop 스트리밍 모드(가상 드라이브)에서 `fs.watch`가 다른 PC의 변경을 알려 주는지, 파일 이름 바꾸기가 원자적인지는 실제 설치에서 확인해야 합니다(설계는 주기 확인을 기준으로 해서 동작에는 지장 없게 함).
- OneDrive "파일 주문형"(Files On-Demand)에서 아직 받지 않은 파일을 읽을 때 내려받기가 끝날 때까지 기다리는지, 오류인지 실기기 확인 필요(4.6의 "덜 받아진 파일 건너뛰기"로 대비).
- 폴더가 OneDrive 공유 폴더인지 앱에서 알아내는 방법.
