# 메모리 사용량 점검 (#107)

> 상태: **측정·검토 완료 (2026-10-24)**. 동작은 바꾸지 않았습니다. 어떤 최적화를 만들지는 사용자가 정합니다(8장 권고표).
> **#109로 A·B·K 구현됨** (엔진·위젯 1.1.1-test.1, 내부 테스트): 결과는 [10장](#10-구현-결과-109).
> 기준: 엔진 1.1.0, 위젯 모두 1.1.0, Electron 44.8.0(Chromium 152, V8 15.2), Windows 11.

한 줄 요약: 위젯 7개(스티키 노트 3장)를 모두 켜면 **프로세스 13개, 작업 관리자 기준 약 290 MB**(전용 작업 집합), 커밋된 전용 메모리는 약 420 MB입니다. **창 하나마다 렌더러 프로세스가 하나씩**(창당 15~30 MB) 생기는 것이 전체의 약 70%이고, 엔진 메인 프로세스가 약 62 MB입니다. 10분 동안 누수로 볼 만한 증가는 없었고, 위젯 관리 창·설정 창은 닫으면 메모리를 모두 돌려줍니다.

## 1. 측정 방법

- 스크립트: [`scripts/memory-profile.js`](../scripts/memory-profile.js) (개발 전용, 제품에 들어가지 않음)

  ```
  npx electron scripts/memory-profile.js [--out <파일.json>] [--quick] [--switch 이름[=값]]
  ```

- 저장소 소스의 엔진을 `--mock-data`와 임시 데이터 폴더로 실행합니다. 실제 설정·두레이 데이터는 건드리지 않습니다.
- 방식은 [`scripts/screenshots.js`](../scripts/screenshots.js)와 같습니다.
  - 모든 창을 화면 왼쪽 12000 px 밖에 둡니다.
  - 오류·확인 대화상자를 막고, 창이 포커스를 가져가지 않게 합니다.
- 켠 위젯: 두레이·시계·캘린더·메일·할 일·시스템 모니터·스티키 노트(노트 3장 열림). 모두 기본 테마입니다. 할 일은 3개, 메일·두레이·캘린더는 예시 데이터를 씁니다.
- 화면 밖 창은 Windows와 Chromium이 "가려짐"으로 보고 멈춥니다. 그래서 바탕화면에 보이는 창처럼 동작하게 설정했습니다.
  - Chromium 가려짐 계산을 끕니다: `CalculateNativeWinOcclusion` 끔, `disable-backgrounding-occluded-windows`.
  - 엔진의 가려짐 판정은 항상 "보임"으로 둡니다.
- 시점: 시작 20초, 2분, 10분, 위젯 관리 창 열기, 두레이 설정 창 추가로 열기, 둘 다 닫은 뒤 10초, 닫은 뒤 70초.
  - 관리 창은 `--settings` 두 번째 실행 신호로 엽니다.
  - 설정 창은 관리 창 페이지에서 `engineApi.openWidgetSettings('dooray')`를 호출해 엽니다.
- 읽는 값:
  - `app.getAppMetrics()`: 프로세스 종류, 작업 집합(WS), 전용 바이트(private bytes), 누적 CPU.
  - Windows 성능 카운터 `Win32_PerfFormattedData_PerfProc_Process.WorkingSetPrivate`: 전용 작업 집합. **작업 관리자 "메모리" 열과 같은 값**입니다.
  - 각 렌더러 프로세스는 그 안의 페이지 주소(`webContents.getOSProcessId()`)로 위젯·창과 짝지었습니다.

세 값의 뜻:

| 값 | 뜻 | 이 문서에서 |
|---|---|---|
| 전용 작업 집합 (PWS) | 이 프로세스만 쓰고 지금 RAM에 올라 있는 메모리. 작업 관리자 "메모리" 열 | **기준 값** |
| 전용 바이트 (Private) | 이 프로세스가 커밋한 전용 메모리. RAM이든 페이지 파일이든 상관없음 | 누수·증가 판단용 |
| 작업 집합 (WS) | 공유 DLL·Chromium 코드 같은 공유 페이지를 프로세스마다 다시 셈 | 합하면 실제보다 훨씬 큼(약 1.2 GB). 합계로 쓰지 않음 |

## 4. 작업 관리자와 비교

- 작업 관리자 "프로세스" 탭은 이 프로세스들을 한 앱 아래에 묶습니다. 설치판은 **Desk Widgets**, 소스 실행은 **Electron**으로 나옵니다. "메모리" 열 합이 위 **전용 작업 집합 합계(약 290 MB)**입니다.
- "세부 정보" 탭의 "메모리(활성 전용 작업 집합)"도 같은 값입니다. "커밋 크기" 열을 켜면 전용 바이트(약 420 MB)에 가깝게 나옵니다.
- 작업 집합 합(약 1.2 GB)은 공유 페이지를 13번 세는 값입니다. 실제 사용량이 아닙니다.
- Windows는 쓰지 않는 페이지를 작업 집합에서 내립니다(트리밍). 그래서 오래 켜 두면 작업 관리자 값이 저절로 줄어듭니다. 전용 바이트는 줄지 않습니다.

## 6. 어디서 메모리가 드는가 (코드 검토)

### 6.1 창마다 프로세스 하나

- 위젯 창 하나가 BrowserWindow 하나이고, Electron은 BrowserWindow마다 새 렌더러 프로세스를 띄웁니다.
  - 테마 창: `engine/main/windows.js`의 `create`
  - 단순 위젯 창: `engine/main/widget-window.js`
  - 알림 카드: `engine/main/notifications.js`의 `createWindow`
  - 위젯 관리·설정·앱 창: `main.js`
- 테마 창은 위젯마다 다른 세션(`partition`)과 주소(`widget-theme://….<위젯>/`)를 씁니다(테마 격리, [테마 호스트 설계](theme-host-design.md)). 그래서 다른 위젯끼리는 한 프로세스를 같이 쓸 수 없습니다.
- 실험 1: Chromium 스위치 `renderer-process-limit=1`
  - `--switch renderer-process-limit=1`로 같은 측정을 했더니 프로세스 수가 그대로였습니다(창 10개 → 렌더러 10개).
  - Electron은 BrowserWindow마다 새 브라우징 인스턴스를 만들기 때문에 이 스위치로는 프로세스가 합쳐지지 않습니다.
- 실험 2: `window.open()`으로 연 창 (작은 시험 앱)
  - 샌드박스 페이지 하나가 `window.open()`으로 창 3개를 열었더니 **창 4개가 렌더러 하나를 같이 썼습니다**. 전용 바이트는 29 MB였습니다.
  - 같은 페이지를 BrowserWindow로 따로 만든 창 하나는 23 MB였습니다.
  - 즉 같은 프로세스에 창을 더할 때마다 드는 비용은 약 2 MB입니다. 따로 띄우면 약 23 MB입니다.
  - 열린 창의 크기·테두리·preload는 `setWindowOpenHandler`의 `overrideBrowserWindowOptions`로 정합니다.
- 같은 세션·같은 출처인 창은 이 방법으로 합칠 수 있습니다. 대상은 스티키 노트 여러 장, 알림 카드 여러 장, 한 위젯의 여러 창(예: 두레이 프로젝트 창)입니다.

### 6.2 숨은 창·닫히지 않는 창

- 위젯 관리 창, 위젯 설정 창, 앱 창(메일 읽기·쓰기, 두레이 분류·규칙), 테마 미리보기, 노트 목록 창은 모두 **열 때 만들고 닫을 때 파괴**합니다. 측정에서도 닫은 뒤 프로세스가 바로 사라졌습니다.
- 알림 카드
  - 대기열로 밀린 카드는 창을 파괴하고, 다시 보일 때 새로 만듭니다(`notifications.js` `hide`).
  - 다만 **카드 하나가 화면에 있는 동안은 창(프로세스) 하나를 계속 씁니다**(약 20 MB). 사용자가 닫지 않는 카드가 여러 장 쌓이면 그만큼 늘어납니다.
  - 대기열 자체(`waiting`·`sources`)는 개수 제한이 없습니다. 창이 없는 데이터라 작습니다.

### 6.3 `backgroundThrottling`·가려진 위젯

- 어떤 창도 `backgroundThrottling`을 바꾸지 않습니다. Electron 기본값(켬)이고, 측정에서도 모든 페이지가 `true`였습니다.
- 메인 프로세스의 일시 정지
  - 사용자 부재(`presence.js`, 3초 확인)에 두레이·캘린더·메일·시스템 모니터 갱신이 멈춥니다. 스티키 노트의 30초 폴더 재검사는 멈추지 않습니다.
  - 가려짐 판정(`window-occlusion.js`)은 시스템 모니터만 씁니다.
- 렌더러 타이머: 두레이 테마 30초, 캘린더 60초, 시계는 다음 분·초에 맞춘 `setTimeout`입니다. 숨김·가려짐에서는 Chromium 기본 스로틀링만 적용됩니다.
- 이런 타이머는 **메모리에는 거의 영향이 없고 CPU도 이미 낮습니다**(합계 코어 1개의 약 0.9%).

### 6.4 preload·이미지·글꼴

- preload는 0.4~3.7 KB입니다.
- 이미지는 트레이·창 아이콘(`engine/assets/icon.png`, 71 KB) 하나뿐이고, 내장 글꼴은 없습니다.
- 큰 스크립트도 40 KB 안팎입니다(`memo/lib/markdown.js` 43 KB, 두레이 `glass/app.js` 39 KB).
- **줄일 만한 자산이 없습니다.**

### 6.6 누수 징후

- 2분 → 10분 사이 메인과 대부분 렌더러의 전용 바이트는 ±0.3 MB 안이었습니다.
- 두레이 테마 창(+5.4 MB)과 캘린더 테마 창(+4.1 MB)은 늘었습니다. 다만 같은 사이에 전용 작업 집합은 거의 그대로였습니다(두레이 +5.8, 캘린더 +2.1). 30·60초 다시 그리기 뒤 V8 힙이 커졌다가 GC 전인 상태와 구분되지 않습니다. **누수 여부를 판단하기에 10분은 짧습니다**(9장).
- 반복해서 쌓이는 리스너
  - `ctx.onStop`(`widgets.js`): 앱 창·위젯 창을 열 때마다 정리 함수를 하나씩 더하고, 위젯이 멈출 때만 비웁니다. 노트나 메일 읽기 창을 여러 번 열고 닫으면 이미 파괴된 창을 잡은 작은 함수가 쌓입니다. 하나에 수백 바이트라 실사용에서는 무시할 수준입니다. 고치기는 쉽습니다(창이 닫힐 때 빼기).
  - `PresenceMonitor.start`는 `powerMonitor` 리스너를 지우지 않습니다. 한 번만 호출되어 지금은 문제없습니다.

### 6.7 koffi (네이티브 호출)

- `user32`·`dwmapi`·`kernel32`·`pdh`를 한 번씩 불러옵니다. 측정 동안 메인 프로세스 증가가 없었습니다.
- 시스템 모니터는 측정마다 PDH 배열용 버퍼를 새로 잡습니다(최대 1 MB, 보통 훨씬 작음). GC가 회수하는 크기입니다.
- 시스템 모니터 설정(간격·기록 길이)을 바꾸면 `SystemMetrics`를 새로 만들고, 그때 같은 이름의 koffi 구조체를 다시 선언합니다. koffi가 같은 이름을 거부하면 배터리·PDH 값이 조용히 빠질 수 있습니다. 메모리 문제는 아니라서 확인하지 않았고, 따로 볼 일입니다.

## 9. 확인하지 못한 것

- **실제 계정 데이터**: 예시 데이터만 썼습니다. 실제 두레이 업무 수, 큰 메일함, 큰 캘린더 구독에서는 메인 프로세스와 두레이·메일·캘린더 창이 더 클 수 있습니다.
- **긴 시간**: 10분까지만 쟀습니다. 두레이(+5.4 MB)·캘린더(+4.1 MB) 창의 전용 바이트 증가가 GC 전 상태인지 누수인지 판단하려면 1시간 이상 재야 합니다. 예: 시점을 늘린 `memory-profile.js`, 또는 `--quick` 없이 시점을 바꿔 실행.
- **설치판**: 실행 중인 설치판에는 렌더러가 없었습니다(위젯 창 없음). 실제로 위젯을 켠 설치판의 수치는 재지 않았습니다. 소스 실행과 같은 Electron이라 비슷할 것으로 봅니다.
- **실제 바탕화면**: 창을 화면 밖에 두고 가려짐 처리를 껐습니다. 실제 바탕화면에서 다른 창에 가려진 위젯은 Chromium이 뒤로 돌려 조금 덜 쓸 수 있습니다.
- **방안 A·B의 실제 절감**: 작은 시험 앱으로 프로세스 공유와 창당 비용(약 2 MB)만 확인했습니다. 노트 페이지(Markdown 편집기)를 여러 장 한 프로세스에 띄웠을 때의 값은 구현해서 다시 재야 합니다.
- **테마 미리보기·메일 읽기/쓰기 창·노트 목록 창**: 이번 순서에 넣지 않았습니다. 모두 렌더러 하나씩(약 16~20 MB) 더하고, 닫으면 사라지는 구조입니다(코드 확인).

### 10.1 무엇을 바꿨나

- **엔진: 창 묶음** ([`engine/main/window-group.js`](../engine/main/window-group.js))
  - 숨은 빈 호스트 페이지 하나(`engine/renderer/group-host.html`)를 띄웁니다. CSP는 `default-src 'none'`이고 preload는 없습니다.
  - 묶을 창은 엔진이 그 페이지에서 `window.open()`으로 엽니다. 그래서 모든 창이 호스트의 렌더러 프로세스를 같이 씁니다.
  - 호스트의 창 열기 처리기는 **엔진이 방금 등록한 1회용 무작위 이름 + 정확한 주소**만 허용하고 나머지는 모두 거부합니다.
  - 묶인 창
    - 자기 `window.open`이 거부되고, 첫 탐색(요청한 페이지) 뒤의 이동도 막힙니다.
    - webPreferences는 `sandbox`, `contextIsolation`, Node 없음, `webview` 없음으로 고정되고, 별도 세션을 쓸 수 없습니다.
    - preload는 예전과 같이 엔진·위젯 코드가 정한 파일입니다.
  - 마지막 창이 닫히고 5초 뒤에는 호스트도 닫아 프로세스를 돌려줍니다.
  - 테마 창(위젯별 세션·`widget-theme://`)은 **묶지 않습니다**. 테마 격리 원칙([테마 호스트 설계](theme-host-design.md))은 그대로입니다.
- **엔진 API: `ctx.createSharedWidgetWindow(opts)`**
  - `createWidgetWindow`와 인자가 같고, 창을 돌려주는 Promise입니다. 위젯마다 자기 묶음을 하나 씁니다.
  - 엔진 API 값(1.6)은 올리지 않았습니다. 위젯은 이 기능이 있는지 확인하고 씁니다([위젯 만들기](widget-dev.md)).
- **A. 스티키 노트** (`widgets/memo/index.js`)
  - 노트 창과 목록 창을 묶음으로 엽니다. 창이 조금 뒤에 생기므로 그 사이에 노트를 닫거나 보관하면 늦게 온 창은 버립니다.
  - 이 엔진 기능이 없는 이전 엔진에서는 예전처럼 창마다 프로세스 하나입니다.
- **B. 알림 카드** (`engine/main/notifications.js`)
  - 카드 창을 묶음으로 엽니다. 창이 오기 전에 카드가 대기열로 밀리거나 닫히면 늦게 온 창은 버립니다.
  - 순서(새 카드가 위)·위치·메뉴(포커스 받기)·버튼·소리·대기열·모두 확인은 그대로입니다.
- **K. 정리**
  - `ctx.onStop`이 취소 함수를 돌려줍니다. 엔진은 위젯 창·앱 창이 닫힐 때 그 창의 정리를 뺍니다.
  - 메일: "더 보기"로 불러온 이전 메일은 30분 동안 다시 페이지를 넘기지 않으면 다음 동기화 때 최근 `cacheSize`통만 남깁니다(`trimLoaded`). "더 보기"로 다시 불러옵니다.
- **종료가 멈추던 문제** (엔진, 변경 전에도 있던 문제)
  - 알림 카드가 표시 한도(기본 3장)를 넘어 대기열에 카드가 있을 때 앱을 끝내면, 닫히는 카드 자리로 대기 카드가 올라오며 **새 창을 열어 종료가 끝나지 않을 수 있었습니다**.
  - 이 문제는 측정 실행(노트 10장 + 카드 3장 + 예시 메일 카드)이 끝나지 않고 트레이 아이콘을 남긴 것으로 드러났습니다.
  - 이제 종료(`before-quit`) 때 `NotificationCenter.stop()`이 카드 창을 닫고, 그 뒤로는 새 카드 창을 만들지 않습니다.
  - 노트는 정상 종료(`clean-exit`)를 크래시로 보지 않습니다.
- **측정 스크립트 안전장치** (`scripts/dev-run.js`, `memory-profile.js`·`screenshots.js`)
  - 트레이 아이콘을 만들지 않습니다.
  - 엔진 종료 절차로 끝내고, 10초 안에 안 끝나면 강제로 끝냅니다.
  - 전체 시간 제한이 있습니다(프로파일 16분, 화면 캡처 실행당 3분).
  - 부모 프로세스가 자식 프로세스 트리를 `taskkill /T`로 정리합니다.
- **덤으로 고친 것** (노트): 이번 실행에서 만든 노트를 페이지가 내용을 읽기 전에 닫으면, 내용이 있어도 빈 노트로 보고 파일을 지울 수 있었습니다. 이제 페이지가 읽은 본문만 "비었다"고 판단합니다.

### 10.2 프로세스가 죽으면

한 프로세스를 같이 쓰므로 **묶음 안의 창은 함께 멈추고 함께 죽습니다**. 예전에는 노트·카드가 하나씩 따로 죽었습니다. 그래서 복구를 넣었습니다.

| 묶음 | 죽었을 때 | 반복될 때 |
|---|---|---|
| 스티키 노트 | 각 창이 `render-process-gone`을 받습니다. 위젯은 페이지가 이미 보낸 내용을 저장하고, 모든 노트와 열려 있던 목록을 0.5초 뒤 **같은 자리에** 새 프로세스로 다시 엽니다(설정의 "열림"은 그대로). 죽기 직전 아직 보내지 않은 입력은 잃을 수 있습니다(예전에 창 하나가 죽을 때와 같음) | 1분에 3번을 넘으면 다시 열지 않고, 다음 위젯 시작 때 열림 |
| 알림 카드 | 화면의 카드마다 새 창을 열고 카운트다운을 새로 시작합니다. 대기열은 그대로입니다 | 1분에 3번째부터는 예전처럼 카드마다 프로세스 하나 |

실제 엔진으로도 확인했습니다(`memory-profile.js --crash-check`). 노트 3장·카드 3장의 렌더러를 강제로 죽였더니 둘 다 새 프로세스 하나로 3장 모두 돌아왔고, 페이지 내용도 다시 그려졌습니다. 확인 대화상자나 화면 표시는 없었습니다.

### 10.3 측정 (전후 비교)

- 방법: 1장과 같습니다. 변경 전은 `main`(엔진·위젯 1.1.0 코드), 변경 후는 이 작업입니다.
- 네 실행을 **하나씩 차례로** 돌렸고, 실행마다 남은 electron 프로세스가 0개인지 확인했습니다.
- 시나리오
  - ① 1장과 같은 구성: 노트 3장, 2분쯤 예시 메일 카드 1장
  - ② 노트 10장 + 확인할 때까지 남는 카드 3장(`--notes 10 --cards 3`)
- 아래 값은 10분 시점입니다.

| 시나리오 | | 프로세스 | 전용 작업 집합 (작업 관리자) | 전용 바이트 |
|---|---|---:|---:|---:|
| ① 노트 3장 + 카드 1장 | 변경 전 | 13 | 280.1 MB | 424.9 MB |
| | 변경 후 | 11 | **261.3 MB** (−18.8, −7%) | **379.6 MB** (−45.3) |
| ② 노트 10장 + 카드 3장 | 변경 전 | 22 | 435.1 MB | 688.3 MB |
| | 변경 후 | 11 | **285.3 MB** (−149.8, −34%) | **407.5 MB** (−280.8) |

묶음별 (10분 시점, 전용 작업 집합 / 전용 바이트):

| 묶음 | 변경 전 | 변경 후 |
|---|---|---|
| 노트 3장 | 프로세스 3개, 45.5 / 82.0 MB | 프로세스 1개(+호스트), 21.3 / 33.2 MB |
| 노트 10장 | 프로세스 10개, 155.1 / 271.3 MB | 프로세스 1개, 34.1 / 45.9 MB |
| 카드 1장 | 프로세스 1개, 16.7 / 29.6 MB | 프로세스 1개(+호스트), 20.9 / 33.4 MB |
| 카드 3장 | 프로세스 3개, 52.7 / 91.4 MB | 프로세스 1개, 23.5 / 37.5 MB |

- **노트·카드 1장을 더할 때마다 약 2 MB**가 듭니다(노트 3 → 10장에 +12.8 MB). 예전에는 약 16~18 MB(전용 바이트 약 27~30 MB)였습니다.
- **창이 하나뿐이면 조금 손해입니다**(카드 1장: 숨은 호스트 페이지 몫 약 +4 MB). 노트 3장만으로도 이득이 이를 넘습니다.
- 메인 프로세스는 변경 전후 63.9 → 66.2 MB, 70.4 → 70.7 MB로 측정 오차(±3 MB) 안이었습니다.
- 위젯 관리 창·설정 창을 열고 닫을 때의 증감도 예전과 같았습니다. 각각 +20 MB 안팎이고, 닫으면 돌아옵니다.
- 창 수가 1~2개 늘어 보이는 것은 숨은 호스트 창입니다. 화면·작업 표시줄에는 나오지 않습니다.

### 10.4 남은 위험과 확인하지 못한 것

- **함께 멈춤**: 한 노트 페이지가 오래 걸리는 작업(아주 큰 노트 붙여넣기)을 하면, 그동안 다른 노트·목록도 입력을 받지 못합니다. 카드도 같습니다.
- **같은 출처**: 같은 묶음의 페이지들은 같은 출처(`file://`)이고 `window.opener`로 서로 닿을 수 있습니다. 모두 같은 위젯(또는 엔진)의 자체 페이지이고 CSP가 인라인 스크립트를 막으므로, 받은 노트 내용이 스크립트로 실행될 수는 없습니다. 테마 같은 외부 코드는 묶지 않습니다.
- **실제 사용 환경**: 실제 바탕화면에서 노트를 끌기·크기 바꾸기·Win+D, 메뉴 클릭, 설치판에서의 동작은 아직 내부 테스트 빌드로 확인해야 합니다. 이번 측정은 화면 밖 창과 단위 테스트입니다.
- **장시간**: 이번 측정도 10분입니다.
- **메일 정리**: 30분 기준 정리는 단위 테스트로만 확인했습니다. 실제 계정에서는 확인하지 않았습니다.
